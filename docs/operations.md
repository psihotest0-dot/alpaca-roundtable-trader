# Operations

## Installation & Setup

1. **Dependencies**: Install using `poetry install`.
2. **Configuration**: Copy `.env.example` to `.env` and fill the variables.
3. **Database Migration**: Ensure the SQLite database schema is applied before startup:
   ```bash
   poetry run alembic upgrade head
   ```

## Upgrading an existing installation

After pulling new code, run `poetry install` and then `poetry run alembic upgrade head`. The revision `c3f1a9e47d52` (2026-11-01) rebuilds `broker_orders` so that orders are keyed by `client_order_id`; it keeps all rows and has a working `downgrade`. A database created before it (for example the old `var/trading.db`) is empty or migrated in place.

## Local Operations Commands

> **With the Docker setup the commands below are run in the container.** Read `poetry run python -m trading_system X` as `docker compose exec trader python -m trading_system X`. The data is in the Docker volume `alpaca_trader_var`; a command run on the host would create a second, empty `var/trading.db`.

- **Config Validation**: `poetry run python -m trading_system validate-config` judges the real configuration: the Alpaca keys must be there (in `.env` or the environment; no dummy keys are made up), every setting must be in range and agree with the others (the position size not above the exposure cap, the risk of a trade not above the total risk, `STOP_LOSS_PCT` and `TAKE_PROFIT_PCT` above zero, the bar sizes the only ones supported), and a name in `.env` that no setting reads (a stale or misspelt key) is warned about, with a suggestion. Only names are looked at: no value is ever printed. Exit 0 if valid, 1 if not. `doctor` warns about the same stale keys.
- **Diagnostics**: `poetry run python -m trading_system doctor [--network]` (Checks Alpaca connection).
- **Candles**: `poetry run python -m trading_system fetch-history [--days 180] [--symbols AAPL,MSFT]` downloads or updates the stored candles (needs the Alpaca keys; run `alembic upgrade head` first). It is safe to run while the system is running, and as often as you like: it only fetches what is missing and checks that the stored prices are still current.
- **Daily bars for the strategy research** (Phase 3b): `docker compose exec trader python -m trading_system fetch-daily [--since 2016-01-01] [--symbols AAPL,SPY]` downloads or updates the daily bars of the research universe (`data/universe.py`: 145 large stocks plus SPY) into its own file `var/research.db` (setting `RESEARCH_DATABASE_URL`), never into `trading.db`. The first run takes about 30 seconds and writes about 394,000 rows; later runs fetch the last week and check the stored prices, like `fetch-history`. The bars come from the full-market feed (SIP), not from `DATA_FEED`: the free IEX feed starts in 2020 and carries 2 to 3 % of the real volume. SIP serves history for free as long as the request ends 15 minutes ago or earlier (the code holds the end back by 16 minutes). A daily bar counts as closed from the next midnight New York time. The command ends with a WARNING for a symbol whose newest bar is more than 5 days older than the others (renamed, delisted, halted: the old name just stops, as MMC did when it became MRSH). `research.db` is a cache with one table and no migrations; it is not backed up (the data can be fetched again); if the shape of `market_bars` ever changes, delete the file and fetch again. The command refuses to run if `RESEARCH_DATABASE_URL` is the same file as `DATABASE_URL`.
- **News** (Phase 5, recording only): `docker compose exec trader python -m trading_system fetch-news [--days 30] [--symbols AMZN,AAPL]` brings the news cache `var/news.db` (setting `NEWS_DATABASE_URL`) up to date from Alpaca's news API (read-only; Benzinga and fiscal.ai) for the research universe and the WATCHLIST (155 symbols). The container `alpaca-trader-news` runs it every 5 minutes (healthy while `var/news_ok` is under 30 minutes old). Each update looks back 2 days from the newest stored article to take in articles the provider changed (about 1 in 40) and carries on from there after a stop (no further back than 30 days; `--days N` fills a longer gap, Alpaca keeps its news from 2015). About 500 articles a working day, text kept as plain text cut to 2000 characters. It is a cache in a file of its own (two tables, no migrations, not in the archives of `trading.db`); the only thing in it that Alpaca cannot give back is the time we first saw an article (`first_seen_at`). When the Oracle is switched on (`ORACLE_ENABLED=true`) the trading loop reads it: each Oracle request carries up to 5 articles about the signal's stock that the cache had stored by then (`OracleRequest.news`, `oracle/news_input.py`): up to 3 from the last 24 hours and up to 2 from the rest of the last week (older than 24 hours, newer than 7 days), newest first, each with its age in hours; round-ups that name more than 3 stocks left out (this one included), the same story once whichever source or day, each cut to a one-line headline of at most 160 characters and a summary of at most 300, with addresses, markup, template tokens, invisible and control characters removed. The ids of the articles it was shown are journalled (`oracle_news` in `audit_events`) so that its verdicts can be judged against them. A cache that cannot be read means an Oracle asked without news, never a lost signal. What puts the articles into the prompt, as quoted data under a line that says so, is the provider (2.2). If a window reaches the 10,000-article limit the command prints a WARNING.
- **Measuring signals** (Phase 3b, step C2): `docker compose exec trader python -m trading_system measure-signals --signal reversal_1w [--horizons 1,2,3,5] [--regime-filter spy200] [--cost 0.001] [--symbols ...]` measures what prices do after a signal on the daily bars in `research.db` (run `fetch-daily` first): one difference to the average of all stocks per day, a Newey-West t, by year and by market regime, checked against the criteria fixed in advance. It never loads the hold-out (from 2026-05-05). Every real signal measured is written to the journal as a `research_trial`; the control `random_tenth` is not. How it measures and what it does not account for: docs/strategy-research-plan.md, section 9. Read-only on Alpaca: it does not call it at all.
- **The weekly signal forward in time** (Phase 3b, experiment of 2026-11-06, no orders): the container `alpaca-trader-forward` runs `fetch-daily` and then `forward-record` every hour (healthy while `var/forward_ok` is under 2.5 hours old). `forward-record` writes, once per trading day and only once the day's bar is stored (a daily bar counts as closed from the next midnight New York time, so the record for a Friday is made on Saturday morning; at least 30 minutes after the close in any case) and before the next open, the stocks that `momentum_12_1` picks, and a random tenth as a control, into `audit_events` (type `forward_picks`, in `trading.db`, which is backed up). `docker compose exec trader python -m trading_system forward-report` judges them as their prices arrive, with the same measurement as `measure-signals`; a verdict only after 60 trading days. A day that was missed stays missed, a record made after the entry open is reported as late and never counted. Rules, criteria and limits: docs/strategy-research-plan.md, section 10.
- **The Oracle observer** (2026-11-06): the container `alpaca-trader-observe` runs `fetch-observe` and then `observe`. `fetch-observe [--days 180]` brings the 15-minute and 1-hour bars of the observation universe (the research universe and the watchlist, 155 symbols, IEX like the live loop) into `var/observe.db` (setting `OBSERVE_DATABASE_URL`; a cache with one table and no migrations, not backed up; downloaded 25 symbols a request and written as each chunk arrives; the first run takes about 12 minutes because Alpaca delivers about 1000 bars a second). `observe` is the live strategy over the observation universe LESS the watchlist (about 133 symbols, the live loop asks about the 22): at every closed 15-minute bar it updates the store, finds the signals of `trend_cross`, and puts each to the Oracle exactly as the live loop does, so the answers land in `oracle_decisions` with the model's own word. **It places no order, ever:** its cycle is built without a risk or an execution engine. Its journal entry is `observe_cycle` (not `entries_cycle`, so `report` stays the live loop's), its heartbeat is `var/observe_heartbeat.json`, and it needs `ORACLE_ENABLED=true` and `ORACLE_PROVIDER=backend` (it refuses to start without them). Why it exists and how its signals are judged: oracle-provider-task.md, section 5 (the change of 2026-11-06).
- **Judging the model**: `docker compose exec trader python -m trading_system judge-oracle` prints how many signals the Oracle has been asked about since the switch-on, how many it answered (approve and veto) and the availability; **until 30 approvals and 30 vetoes are in and 80 % of the asked signals got a REPLY it shows nothing else** (a reply is an approve, a veto or the model's own HOLD; only silence, a timeout or a refused token counts against; the HOLDs are shown apart and stay out of both groups) (no return is even computed: no peeking). Then it takes THE look: every answered signal is played out as a shadow trade (same entry plan, stop, target and costs as the backtest, bars from `var/observe.db`), approved and vetoed by the same rule, compared with Welch's t, with the halves of the period and a random-relabelling control, and the verdict is `helps`, `hurts`, `cannot be told from noise` or `control suspect`. A look is journalled (`oracle_judgement`); the second is possible at 60 + 60 with a bar of 2.5, then none. Trades that have not reached their stop or target yet are left out and do not use the look. **It judges one period at a time**, a period being a model and the backend's `prompt_version` (the label the backend returns since 2026-11-06 22:11 German time, stored by the bot in `oracle_decisions.prompt_version`): answers under another model or label are never pooled with it and are listed with counts only, answers from before the label existed are their own "unlabelled" period, and the looks (one, then a second at double the minimum) are counted per period and journalled with it. Rules and the reason for each: oracle-provider-task.md, section 5.
- **Judging the strategy candidates**: `docker compose exec trader python -m trading_system judge-candidates` (research-plan section 12.1). The observer journals the signals of `trend_cross_session` and `trend_cross_session_late` and of the live `trend_cross` (the control) over the same bars, no orders, no Oracle question. The command prints the number of trading days run, the passes in which a candidate broke (should stay 0), and per candidate the mature signals and trades; **it prints nothing else until 150 mature trades and 40 trading days** (the 40-day minimum is the limit: about 8 January 2027 at the earliest; on Friday's stored bars the control gave about 16 signals and each candidate 17 over 10:00 to 15:45 New York, so the trades will be there long before). Then it takes THE look (journalled as `candidate_judgement`, never repeated for the same sample); a second look is possible at twice the trades of the first look (at least 300) with a higher bar, and there is no third. `helps` is a reason to look further, never a reason to switch the live loop. The same command prints a second block for the ATR exit candidate (research plan, section 13.1; bar t 2.4 / 2.7): the recorded signals of the live strategy played out with the live exit and with a stop at 6 ATR and a target at 7.5 ATR, paired per signal, same minimum and same two looks. Offline: `backtest --atr-stop 6 --atr-target 7.5` replays the stored candles with that exit (descriptive; the live loop never reads it).
- **Is the candidates' record running?** (read-only) `docker compose exec -T trader python -c "import sqlite3; c = sqlite3.connect('file:/app/var/trading.db?mode=ro', uri=True); print(c.execute(\"select event_type, count(*), min(timestamp), max(timestamp) from audit_events where event_type in ('candidate_signal','candidate_cycle') group by 1\").fetchall())"` prints the number of `candidate_cycle` rows (one per successful pass of the observer, about 26 a session) and `candidate_signal` rows (the control and the two candidates; about 16 a session each on Friday's bars). `judge-candidates` shows `trading days run` and `passes in which a candidate broke` (should stay 0); mature signals and trades are 0 for the first 14 days by design (maturity), so an empty verdict in the first weeks is normal. If `candidate_cycle` stays empty on a trading day: `docker compose logs observe | grep -i candidate`.
- **Hours research** (2026-11-06): `docker compose exec trader python -m trading_system measure-intraday --signal orb_30m_long` measures the opening-range breakout on the 15-minute bars of `var/observe.db` (development part only; the last two months, from 2026-09-08, are never loaded), the same way as `measure-signals` measures the daily ones: one value a day, minus all stocks over the same window, Newey-West t, a flat cost, by month. `--signal random_entry` is the control and is not counted. Definition, criteria and limits: docs/strategy-research-plan.md, section 11, written before the first result.
- **Corporate actions** (2026-11-06, read-only): `docker compose exec trader python -m trading_system corporate-actions [--symbols AAPL,MSFT | --universe] [--ahead 30] [--back 0]` lists the splits, spin-offs, mergers and renames that hit (or are about to hit) our stocks; by default the symbols of the open positions and orders plus the watchlist, with `--universe` the research universe too. Dividends are left out (the prices are adjusted for them). Alpaca announces an event only a few weeks ahead, so "nothing found" is never a promise; the bars are adjusted for splits only, so a spin-off or a merger still shows in them as a price jump (RTX, 2020-04-03: the command shows it as `renamed UTX -> RTX` and a 1-for-2 split). `doctor --network` ends its Alpaca check with the same look at what we hold over the next 7 days: a WARNING line, advisory, never a failure. Why it is built the way it is (the API cuts an answer at 1000 events without a word): the docstring of `data/corporate_actions.py`.
- **Equity against Alpaca's history** (2026-11-06, read-only): `docker compose exec trader python -m trading_system equity-check [--days 30]` compares the account's equity as our journal recorded it (the last `entries_cycle` pass of each New York day) with the end-of-day equity Alpaca keeps for the same days. Exit 0 if every compared day agrees within 0.5 % (an arbitrary tolerance, see `observability/equity_check.py`), 1 if one differs or if there was nothing to compare. A day Alpaca has and the journal lacks is listed (the bot was down, or the journal had not begun) but is not a failure. While the bot only dry-runs the equity is flat and the check proves little; it is there for the day real paper orders flow.
- **Backtest**: `poetry run python -m trading_system backtest [--days 60]` replays the stored candles. The first days of the window are warm-up for the indicators. It takes a few seconds for 90 days (3.6 s of computing for 22 symbols; the strategy is asked only about symbols that could signal, and sees the same window of history as the live loop). The report ends with the signals that did not become a trade and why.
- **Dry Run**: `poetry run python -m trading_system run --dry-run` (Executes the loop without sending API orders).
- **Paper Run**: `poetry run python -m trading_system run --paper` (Live paper trading against Alpaca).

## Control & Incidents

### Pause / Resume (Kill Switch)
- **Pause**: `poetry run python -m trading_system pause-entries`
  This acts as a manual kill switch. It stops any *new* entries from being submitted. Open positions are not automatically liquidated.
- **Resume**: `poetry run python -m trading_system resume-entries [--force]`
  Looks at the account again before it lifts the halt: it refreshes the orders from the broker and checks that every position has an active stop and that no order we sent is unknown to the broker. If it finds a problem it lists it and the halt stays (exit 1). `--force` lifts the halt over the problems, for when you have seen them and decided to go on. If entries are not halted it does nothing.
- **Reconcile**: `poetry run python -m trading_system reconcile` is that same look, on demand and on its own: it refreshes the orders, reports the positions and open orders and the problems, and exits 0 if the account agrees with our records, 1 if not. It trades nothing, halts nothing and closes nothing.
- **Status**: `poetry run python -m trading_system status`
  Shows whether entries are halted and the daily loss baseline (start-of-day equity and the trading day it belongs to).

### Is it healthy? (Phase 6)
- `docker ps` (or Docker Desktop) shows `healthy` / `unhealthy` for each container. `docker compose exec trader python -m trading_system health` says why: it reads the heartbeat file the loop writes every tick (`HEARTBEAT_PATH`, default `var/heartbeat.json`) and exits 1 with the reasons if the loop stopped ticking, cannot read the market clock, has not looked at a bar for 20 minutes with the market open, or its last look-up had signals that broke before they became orders.
- `alpaca-trader-data` is healthy while its last successful download is under 2.5 hours old (`var/data_ok`); `alpaca-trader-backup` while an archive under 7 hours old exists in `var/backups`.
- An alert is a `CRITICAL` log line that starts with `ALERT:` (a signal broke in risk or execution; the whole look-up crashed): `docker compose logs trader | grep ALERT`. Docker does not restart an unhealthy container by itself; it only shows it.
- `docker compose exec trader python -m trading_system report [--date YYYY-MM-DD]` is the day in numbers (a New York trading day; today by default): passes over a bar, signals, how many became an order, how many broke, risk decisions with the reasons for refusals, orders (simulated or not), fills, the equity at the first and the last pass, the alerts. A quiet failure shows as `BROKE` and `ALERTS`.
- What each pass over a bar did is in the table `audit_events` (type `entries_cycle`), and the risk decision of every signal, with its reason, is in `risk_decisions`.

- The containers run as an ordinary user (`trader`, uid 10001), not as root. A **new** volume takes its ownership from the image. A volume made while the image still ran as root (the `alpaca_trader_var` of 2026-11-03 was one) needs this once, with the containers stopped and a fresh archive taken first: `docker run --rm -v alpaca_trader_var:/v alpine chown -R 10001:10001 /v`. A restored database file (see the restore steps) needs the same owner: add `&& chown 10001:10001 /app/var/trading.db` to the restore command.
- Logs: `var/alpaca_trading.log` is rotated (5 files of up to 5 MB) and only the `run` process writes it; everything also goes to the container's output (`docker compose logs`), which Docker keeps to 3 files of 10 MB per container.

### Incident Procedures
- **Reconciliation**: If the system crashes mid-submission or enters an unknown state, it halts entries. The `reconcile_order` function attempts to recover status on restart.
- **Unprotected Positions**: The check `emergency_check_unprotected_positions` runs on every tick of the runner, also while entries are halted or the market is closed. A position without a covering stop halts new entries and raises an alarm; it is not sold. Closing it at market happens only with `EMERGENCY_CLOSE_UNPROTECTED=true` (default `false`). Undo the halt with `resume-entries` after checking the account.

## Database Backup and Restore (SQLite)

- **Automatic archive (Docker setup)**: the container `alpaca-trader-backup` runs `python -m trading_system backup-db --out /backups --keep 28` at start and then every 6 hours (`BACKUP_INTERVAL_SECONDS`, `BACKUP_KEEP` in `.env`). The archives land on the PC, in `./var/backups/trading-YYYYMMDD-HHMMSS.db.gz` (UTC), outside Docker, so they survive a reset of Docker Desktop or `docker compose down -v`. Each one is a consistent snapshot made with SQLite's backup API (a plain file copy would miss what is still in the `-wal` file), it is checked (`integrity_check`, a migration revision present) before it is kept, it is written under a temporary name and renamed when complete, and old archives are removed only after a new one is safely there. A failed backup prints `Backup FAILED` (`docker compose logs backup`) and is retried at the next interval; nothing already archived is touched. One archive is about 4 MB (the candles are most of the database and compress well). Only files named `trading-YYYYMMDD-HHMMSS.db.gz` are ever deleted; anything else in the folder is left alone. A backup can also be taken by hand: `docker compose exec backup python -m trading_system backup-db --out /backups`.
- **Restore (Docker setup)**: (1) `docker compose stop trader data backup`. (2) Choose an archive in `var/backups`. (3) Put it into the volume (Git Bash: prefix with `MSYS_NO_PATHCONV=1`):
  ```bash
  docker run --rm -v alpaca_trader_var:/app/var -v "$PWD/var/backups:/backups:ro" alpine sh -c \
    "rm -f /app/var/trading.db /app/var/trading.db-wal /app/var/trading.db-shm && gunzip -c /backups/trading-YYYYMMDD-HHMMSS.db.gz > /app/var/trading.db && chown 10001:10001 /app/var/trading.db"
  ```
  (4) `docker compose up -d`, then `docker compose exec trader python -m trading_system status`, and reconcile the broker state before resuming entries. To try an archive without touching the live data, do step 3 into a scratch volume (`docker volume create alpaca_restore_test`, mount that instead of `alpaca_trader_var`), run `status` and `alembic current` on it with the image, and remove the volume. That was done for the first archive on 2026-11-03: integrity ok, revision `b6d1f4a82c35`, the daily baseline present.
- **Backup**: SQLite stores the entire state in a single file (default: `./var/trading.db`; in the Docker setup it is `/app/var/trading.db` in the volume). To back up safely while running (using WAL mode):
  ```bash
  sqlite3 ./var/trading.db ".backup './var/trading_backup.db'"
  ```
  In the Docker setup (the image has no `sqlite3` command, Python does the same):
  ```bash
  docker compose exec trader python -c "import sqlite3; s=sqlite3.connect('var/trading.db'); d=sqlite3.connect('var/backup.db'); s.backup(d); d.close()"
  docker cp alpaca-trader:/app/var/backup.db ./var/backups/trading-$(date +%F).db
  ```
- **Restore**:
  1. Stop all users/processes interacting with the database.
  2. Backup existing state (even if corrupted) before overwrite. Ensure WAL and SHM files are handled/removed.
  3. Copy the backup file over the active database file:
     ```bash
     cp ./var/trading_backup.db ./var/trading.db
     ```
  4. Run integrity and schema checks:
     ```bash
     sqlite3 ./var/trading.db "PRAGMA integrity_check;"
     poetry run alembic upgrade head
     ```
  5. Run `reconcile` and, if the entries are halted, `resume-entries`: both look at the broker again.

## Docker & Connectivity

- **News cache**: `var/news.db` (`NEWS_DATABASE_URL`), a SQLite file of its own in the same volume, filled by the container `alpaca-trader-news` (see `fetch-news` above). Chroma is gone (2026-11-05); there is no vector store to run.
- **Containers** (`docker compose up -d`): `alpaca-trader` runs the trading loop (`run`, dry-run: real data, simulated orders; it does not use `--paper`) and `alpaca-trader-data` runs `fetch-history --days 180` once an hour. Both run `alembic upgrade head` first and share the named volume `alpaca_trader_var`, mounted at `/app/var`: that volume is the only copy of the data (`trading.db` with the state, signals, orders and the `market_bars` candles, and the log). The host's `var/` is not mounted on purpose (SQLite in WAL mode does not work reliably over a Windows bind mount, and a host copy would diverge). Both restart by themselves (`unless-stopped`) when Docker Desktop starts. `docker compose logs -f trader` follows the loop; `docker compose stop trader` is a clean stop (SIGTERM). Only `ALPACA_API_KEY`, `ALPACA_SECRET_KEY`, `IS_PAPER` and `DATABASE_URL` reach the containers; nothing else from `.env`. `docker compose down` keeps the data; `docker compose down -v` deletes it. After a code change: `docker compose build && docker compose up -d`. One-off commands: `docker compose exec trader python -m trading_system status`, or `docker compose run --rm app …` when the loop is not running.
- **Database**: the trading state is the project's own SQLite file. The Go backend's containers and their SQL database are separate and are not used by this project.
- **Host services from a container**: the container reaches the Go backend (on the PC's `127.0.0.1:8080`) as `http://host.docker.internal:8080`; Docker Desktop forwards that to the PC's loopback (checked 2026-11-05 and 2026-11-06, `/healthz` 200). Never `127.0.0.1` from inside the container, which is the container itself. On plain Linux Docker add `extra_hosts: ["host.docker.internal:host-gateway"]` to the service. Side effect to know: from a container the whole backend is reachable, not only the Oracle routes.

## The Oracle through the Go backend (task 2.2)

The bot asks the backend (`POST /oracle/evaluate`), never the model. Off by default.

**Turning it on** (in the bot's `.env`, which is git-ignored; the same token as the backend's `ORACLE_TOKEN`, at least 32 characters, made with `python -c "import secrets; print(secrets.token_hex(24))"`):

```text
ORACLE_ENABLED=true
ORACLE_PROVIDER=backend
ORACLE_MODE=shadow            # the default; active only by a separate decision
ORACLE_BACKEND_TOKEN=<the token>
```

(`compose.yaml` also takes the backend's own name, `ORACLE_TOKEN`, when `ORACLE_BACKEND_TOKEN` is not set; the bot's name wins if both are.) Then `docker compose build && docker compose up -d`. Only the `trader` service gets these variables (not `data`, `news`, `backup`). Check with `docker compose exec trader python -m trading_system validate-config` (warns about a missing or short token; prints no value), `doctor --network` (pings the backend: token accepted?) and `oracle-probe` (one ARTIFICIAL signal marked `oracle-probe`; shows the model's real answer, writes one row each to `strategy_signals` and `oracle_decisions`, places no order).

**Modes.** `shadow`: the model is asked and the answer recorded, but the loop is told `APPROVE` whatever it said, so orders do not change; the record holds the model's own word, with `mode = 'shadow'`. `active`: the verdict counts (`VETO` ends the signal, `HOLD` waits), and a failed call is a `HOLD` that failed, so a backend that is down means no entries. The order for a signal is: risk takes a cheap first look (a refusal is recorded once and the model is not asked), then the model, then risk decides on a fresh snapshot.

**When something is wrong** (the cause is the `error_kind` of the row in `oracle_decisions` and the `kind` label of `oracle_answers_total`): `unauthorized` = the token is missing or differs from the backend's; `unavailable` = the backend is not running, its Oracle route is off (404: `ORACLE_TOKEN` unset or shorter than 32 there) or the model behind it is down (502); `timeout` = no reply in `ORACLE_TIMEOUT_SECONDS` (10) or the backend's own 504; `bad_request` = the backend refused the request (a bug here); `bad_reply` = what came back is not the contract. After a failure the client does not call again for 30 seconds (the rest of that bar's signals fail at once), and asks again on the next tick; the backend finishes a call the bot stopped waiting for and keeps the answer (3 minutes for a `HOLD`, 30 for a final verdict). `health` pings the backend each minute: in shadow mode a failure is only a warning in its output (`healthy (warning: ...)`), in active mode the container turns `unhealthy`.

**Judging the model** is a separate, written-down procedure: `oracle-provider-task.md`, section 5 (minimum numbers, one look, no peeking). Do not run `--replay-oracle` on the recorded decisions before the minimum is reached.

## Metrics: Prometheus and Grafana through the Go backend's stack (2026-11-07)

**What runs.** The two loops, `alpaca-trader` (the trading loop) and `alpaca-trader-observe` (the Oracle observer), serve their numbers as a web page in the Prometheus text format (`METRICS_ENABLED=true` in `compose.yaml`; `data`, `news`, `forward` and `backup` have no loop and no metrics page). Inside the container the page is on `0.0.0.0:9100` (the host cannot reach a container's `127.0.0.1`); on the PC it is at `http://127.0.0.1:9101/metrics` (trader) and `http://127.0.0.1:9102/metrics` (observer). **Loopback only, because the page has no password**: the mapping in `compose.yaml` is `127.0.0.1:9101:9100`, never `9101:9100` (which Docker would publish on every interface; `tests/unit/test_ops_artifacts.py` fails on that). A port that cannot be taken is one `ERROR` line in the log and nothing more: the metrics are an addition and cannot stop the trading.

**Who reads them.** The backend's `go-prometheus-1` (job `alpaca-trader`, targets `host.docker.internal:9101` and `:9102`, 15 s; in the backend's `prometheus/prometheus.yml`) and its Grafana `go-grafana-1` (http://127.0.0.1:3000, dashboard "Trading bot (alpaca)"; Prometheus itself is at http://127.0.0.1:9090). Our compose does **not** join the backend's network, so the bot starts and trades with the backend's stack stopped; the targets are then simply DOWN over there. The backend's session edits its own files; we send it text. Its Prometheus keeps the series 15 days in the named volume `go_prometheus_data`. Series of the bot all start with `alpaca_`, so none can collide with the backend's own. **The two targets carry a label `service`** (`trader` for `:9101`, `observer` for `:9102`), set with `labels:` in the backend's `prometheus/prometheus.yml`. It is not decoration: an unlabelled gauge is exported as `0` from the first scrape, before anything sets it, so the observer exports the trader-only gauges (account, positions, `alpaca_unprotected_positions`, the protection-check and reconcile timestamps) as `0` for good, and a timestamp of `0` looks infinitely stale. The rules and panels that read those series carry `{service="trader"}` (a pytest fails without it). **If the label is missing from the target, they match nothing and never fire**: after any change of the backend's `prometheus.yml` check that `up{job="alpaca-trader"}` still shows `service`.

**The files are in `ops/`** and are the source of what the backend's repository holds: `ops/prometheus/alpaca_alerts.yml` (the rule group `alpaca-trader`), `ops/prometheus/alpaca_alerts_test.yml` (promtool cases: each rule has one that fires and one that stays quiet) and `ops/grafana/alpaca-trader.json` (the dashboard). Test the rules with promtool from the repository root:

```bash
docker run --rm --entrypoint promtool -v "$PWD/ops/prometheus:/etc/prometheus:ro" prom/prometheus:v3.15.0 test rules /etc/prometheus/alpaca_alerts_test.yml
```

(On Git Bash for Windows put `MSYS_NO_PATHCONV=1` in front and use `$(cygpath -m "$PWD/ops/prometheus")`.) The pytest `tests/unit/test_ops_artifacts.py` holds every `expr` of the rules and the dashboard against the metrics the process really publishes, so a renamed metric breaks the build instead of blanking a panel. **A rule that fires is delivered** (since 2026-11-08): the backend's Alertmanager (`go-alertmanager-1`, http://127.0.0.1:9093, config in the backend's `alertmanager/`) sends `critical` and `warning` alerts to the owner's Telegram chat, grouped by alertname, the first message after 30 s, repeated every 6 h (every 2 h for `critical`), with a notice when it resolves; `info` is never sent. The message is plain Bulgarian text (`🔴 СПЕШНО` / `🟠 Внимание` / `✅ Мина: <alertname>`, then `[service] summary` and the description). The state is also a row at http://127.0.0.1:9090/alerts and in Grafana under Alerting. **Critical:** `AlpacaLoopStalled`, `AlpacaUnprotectedPositions`; the other six are warnings. **A planned restart of the bot's containers** (an image deploy) can send one firing and one resolved notice for `AlpacaTargetDown` (it waits 5 minutes, and the observer runs `fetch-observe` before its page is up: seconds normally, minutes after a long gap); tell the backend's session before a deploy if you want it warned. The backend has its own Oracle alerts (`OracleGivesNoVerdict`, `OracleCallsRefused`, `OracleSlow`, from the calls it sees); the bot has none of its own for the Oracle, only the panels, for comparison.

**What is published** (in `observability/metrics.py`; counters carry `_total` on the wire):

| series | where | meaning |
|---|---|---|
| `alpaca_heartbeat_timestamp_seconds`, `alpaca_market_open`, `alpaca_last_entries_timestamp_seconds` | both loops | the loop ticks (every minute with the market open, every 5 minutes closed); what the broker's clock says; the last look for entries that completed (stale on purpose while the market is closed) |
| `alpaca_entries_passes_total{outcome}`, `alpaca_signals_total`, `alpaca_entries_errors_total` | both | looks for entries by outcome (`ok`, `skipped`, `retry_later`, `crashed`), signals found, signals that broke before they became orders plus crashed looks |
| `alpaca_oracle_answers_total{verdict,kind}`, `alpaca_oracle_errors_total`, `alpaca_oracle_latency_seconds` | both | the bot's view of its Oracle calls (kind: `answer`, `cached`, or the cause when there was no answer) |
| `alpaca_rejected_signals_total{reason}` | trader | risk said no (the reason is cut at its first colon, so numbers cannot make new series) |
| `alpaca_account_equity`, `alpaca_active_positions`, `alpaca_gross_exposure` | trader | the account, read after each look for entries |
| `alpaca_unprotected_positions`, `alpaca_protection_check_timestamp_seconds`, `alpaca_reconcile_timestamp_seconds` | trader | positions without a stop; when the protection check and the order reconciliation last succeeded. **A `0` in `alpaca_unprotected_positions` means "all protected" only while the timestamp is fresh**: a check that cannot read the broker changes neither |
| `alpaca_candidate_signals_total{strategy}`, `alpaca_candidate_errors_total` | observer | the strategy candidates run forward in time (research plan 12.1 and 13.1) |

**Not published on purpose.** Some metrics were defined long ago and are set by nothing (`runtime_health`, `market_data_age_seconds`, `reconciliation_age_seconds`, `reserved_entries`, `planned_open_risk`, `daily_loss`, `order_failures`, `unresolved_intents`). A gauge nobody sets reads `0`, which on a dashboard looks like "all is well". They sit in a private registry (`metrics.NOT_WIRED`) that no server exposes, and move into the published block only together with the code that sets them and a test. **Write no rule on them.**

**Adding a metric.** Set it from the code through one of the small never-raising helpers at the end of `metrics.py`, put it in the published block, test it, and only then use it in a rule or a panel (the pytest above fails on a name the process does not publish). Keep labels few and bounded (a reason, a verdict, a strategy; never a symbol, an order id or a signal id).

**Check by hand.** `curl -s http://127.0.0.1:9101/metrics | grep ^alpaca_` (and `:9102`); the targets are UP at http://127.0.0.1:9090/targets; a query in Grafana's Explore: `time() - alpaca_heartbeat_timestamp_seconds` is a few seconds to 5 minutes for a living loop.

## Docker image

The image is built from `Dockerfile` on Python 3.15, the version the project is tested on (CI
runs on 3.15 too; moved from 3.11 on 2026-11-13, see docs/decisions.md). Another minor only together
with CI and `poetry.lock`: every locked package must have a wheel for it.
It contains runtime dependencies only: no pytest, ruff, mypy or safety, and never `.env` or `var/`.

```bash
docker build -t alpaca-roundtable-trader:latest .
docker run --rm alpaca-roundtable-trader:latest python -m trading_system --help
# Keep the database and logs outside the container:
docker run --rm -e ALPACA_API_KEY=... -e ALPACA_SECRET_KEY=... -v "$PWD/var:/app/var"     alpaca-roundtable-trader:latest python -m alembic upgrade head
```

`docker compose build` produces the same image name. CI builds the image and smoke-tests it on every
push and pull request. Do not change the Python tag on its own; change it together with `pyproject.toml`
and the CI Python version.

## Simulation Limitations
- **Backtest Fills**: Conservative assumptions apply (assume stops hit first if both triggered in same bar).
- **Paper Fills**: Slippage is generally zero on limit orders in paper environments compared to live. Real market depth is not fully simulated. Survivorship bias exists as the watchlist is fixed in testing.
