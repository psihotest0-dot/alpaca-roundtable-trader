# Decisions

- **Dependency Manager**: We chose `poetry` to ensure reproducible builds across local, CI, and Docker environments via `poetry.lock`.
- **Database**: SQLite is used for the MVP to minimize setup friction and keep local persistence simple. This project keeps its state only in its own file (`var/trading.db`); the SQL database in the Go backend's Docker containers belongs to that backend and is not used here (owner, 2026-11-02).
- **Scope**: The MVP strictly implements paper trading. Live trading features have been explicitly excluded.
- **Chroma**: *removed on 2026-11-05 (owner's decision of 2026-11-02, carried out).* The news are kept in a SQL cache, `var/news.db` (see the decisions of 2026-11-05).

## Decisions of 2026-11-01

Owner decisions and the engineering decisions that follow from the analysis (`analysis-and-update-plan.md`).

**Product**
- **Oracle answers yes / no / hold** (`APPROVE` / `VETO` / `HOLD`) and nothing else: it never proposes orders, sizes or prices. `HOLD` means "not now, ask again next cycle while the signal is valid"; `VETO` is final for that signal. Risk keeps the last word.
- **AnythingLLM is gone.** Its code and settings were removed in Phase 2 and its documents in 2.4. The Oracle is an interface (`OracleProvider`, answers `APPROVE` / `VETO` / `HOLD`); `NullOracle` is the only provider so far. The real model will be served by a Lemonade server behind the owner's chat-only Go backend, with a Flet UI. **All trading logic stays in this Python project**; there is no plan to port it to Go. Provider details are still open.
- **Live trading is a future goal.** Today the system is paper-only (enforced in `Settings` and `AlpacaBroker`); Risk, Execution and reconciliation are built as if real money were at stake.
- **News come after the core is stable**, starting with the Alpaca News API (symbol-tagged) rather than RSS keyword matching.

**Engineering**
- **Work goes straight to `main`** (no feature branches), which is why every push is preceded by ruff, mypy and pytest, plus the CI steps on a fresh clone when dependencies, the Dockerfile or migrations change.
- **Python 3.11 everywhere** (pyproject, CI, Docker). The locked numpy/onnxruntime/pandas do not install on newer minors; Dependabot is told to ignore Python major/minor bumps for the image.
- **Ruff rules are pinned** (`E4, E7, E9, F`) because the default set grows between releases. The ruff version in `.pre-commit-config.yaml` must equal the one in `poetry.lock`.
- **Repositories run one committed transaction per call.** No long-lived sessions: they never committed, held SQLite's write lock and became unusable after one failed flush.
- **An order is identified by its `client_order_id`** (generated by us before anything is sent); `broker_id` is nullable until the broker answers. Migration `c3f1a9e47d52`.
- **The daily loss guard measures from the previous close** (`account.last_equity`, the broker's own basis for day P&L) or, if absent, the equity at the first cycle of the day. One baseline per New York trading day, never moved within the day, and a baseline from another day is rejected.
- **Market data:** one bulk request for all symbols per timeframe, prices adjusted for splits and dividends, one canonical bar shape (`data/bars.py`). Known gap: IEX bars include extended hours (Phase 4 adds a regular-session filter).
- **Retries only for transient failures** (network, timeouts, HTTP 408/429/5xx). Bugs and 4xx fail at once.
- **Dependabot updates are merged together, after checking the combination**; `poetry.lock` conflicts are resolved with `poetry update <pkg> --lock`, never by hand.

## Decisions of 2026-11-02

- **Entry limit buffer stays 0.1 %.** The strategies will be thought through later.
- **Stopping the system does not pause entries.** A restart carries on by itself. `PAUSE_ON_SHUTDOWN=true` or `run --pause-on-exit` make the next start wait for `resume-entries`.
- **An unprotected position halts and raises an alarm; it is not closed automatically.** Closing at market needs `EMERGENCY_CLOSE_UNPROTECTED=true` (default `false`). Bracket orders are `GTC`, because the legs inherit the entry's time in force and a `DAY` bracket loses its stop at the close.
- **The model connection (Phase 2.2) is postponed to the end.** The owner will show the Go backend and the Flet app first. Until then the Oracle is `NullOracle`.
- **Market data and news go to SQL tables; Chroma is removed.** One table holds the market data from Alpaca (candles first), one holds the news (articles from RSS and, later, from the Alpaca News API, told apart by a `source` column). Chroma, the chunker and the embeddings go with it: what the Oracle needs is "the news for this symbol in the last hours", a lookup by symbol and time, not a similarity search. The candle table is built (Phase 3.2, below); the news table is not. The Chroma code stays until the news table replaces it, so that the RSS collector never writes into nothing; the news table and the removal of Chroma belong to Phase 5.
- **Candle store (Phase 3.2).** The owner left the choice of the price basis to the engineer (2026-11-02). Table `market_bars` in `trading.db` (migration `b6d1f4a82c35`), filled by `fetch-history`. Prices are adjusted for splits and dividends (`Adjustment.ALL`), the same basis as the live loop, so a backtest sees the series the system trades on. Alpaca re-adjusts the whole past whenever a split or dividend goes ex, so a stored copy turns stale and old and new rows on different bases would show a price gap that never happened. Therefore every update downloads the last 7 days again and compares the oldest bars both copies share (20 bars, tolerance 0.01 %); if they disagree the symbol's history is downloaded again from the start. The overlap also catches late corrections of recent bars. Only closed bars are stored. Bars outside the regular session are stored as they come and filtered when read (Phase 4). The table lives in `trading.db`, not in a separate file: measured 17.7 MB for 22 symbols and 180 days (about 36 MB a year), and one database means one migration framework and one backup. Measured: a full download of 180 days takes 73 s, an update 4 s; the live loop still downloads 30 and 90 days on every cycle (about 21 s), and switching it to the store is a separate step.
- **Owner's idea for the Oracle input:** the data from Alpaca plus, when an RSS item matches the symbol, a short summary of it; the model then answers `APPROVE` / `VETO` / `HOLD`. News text is the first outside text in a request, so Phase 5 needs prompt-injection handling for it (a length-limited summary, no URLs or commands, framed as data, not instructions).

## Decisions of 2026-11-03

- **What the owner wants, and the next task (2026-11-03).** Goals: to learn, to try a model (the Oracle), and later real profit (out of scope until Phase 7 and a separate decision; `IS_PAPER` still refuses anything else). Horizon: **not one but three separate strategies, one for hours, one for days and one for weeks** (the first note of the day said "weeks" only; that was a misunderstanding: the owner had read my question about the strategy's horizon as a question about training and testing time, and corrected it the same day). Hours means 15-minute and hourly bars (the live loop and the 180 days of candles we have are the base); days and weeks mean daily bars, so the research needs daily bars and several years of history. The method (steps C1 to C6) is the same for each of the three, but each has its own candidate, hold-out and paper period, and the Phase 3 gate applies to each one separately. The live loop is left as it is. Open because of this: the order of the three, the share of the account and of the risk each gets (the `RiskEngine` limits are shared today), and how an order is attributed to its strategy. The next task is Phase 3b, the strategy research in `strategy-research-plan.md`: first shaped with the owner, then built. Its shape: more years of data, signals judged by what prices do after them (not by an account simulation, which at 141 trades cannot see an edge below about 0.8 % a trade), a hold-out period and a count of every variant tried, a backtest only for candidates, and the model and news judged forward in time only, because a backtest of a model on old news is contaminated by what the model has already seen.

- **Phase 3 ends as a tool, and its gate is not met (3.4, 3.5).** The backtest now reports the expectancy of a trade, a daily Sharpe, the result period by period with the same parameters, by symbol, and at higher costs; the Oracle's vetoes are played out as shadow trades and compared with the trades that were made, with a t-test of the difference (a verdict of "helped" or "hurt" only at |t| >= 2). No parameter search was built: the strategies are being left for later, and a walk-forward that fits parameters on one stretch and tests on the next only means something once there is a search. A result without a fit is checked for steadiness over periods instead. On all 180 days of candles no strategy has a positive expectancy (live `trend_cross` -0.63 %, t = -0.2), and the live one is about zero before costs. The plan's rule (section 9 of the action plan) is that without a positive expectancy out of sample the work does not go on to Phases 4 and 7. What to do about it is the owner's call.

- **Strategies are plugins behind `BaseStrategy`, and they are compared on the same footing (Phase 3.3a).** A strategy only turns closed bars into LONG signals; sizing, the position limit, the daily loss guard, the entry plan, fees and slippage belong to the risk and execution engines and are the same for every strategy, so a difference between two rows of `compare-strategies` is the strategy's (or noise). The original Money_bot's two strategies are ported from its source on GitHub (`psihotest0-dot/Money-bot`, `tools/indicators.py`); they are a trend with a pullback to the fast EMA, not crossovers, whatever the class names say, and the port keeps every rule except the three the plan changed (long only, closed bars, the risk engine sizes). The live loop does not take its strategy from the registry: it runs `trend_cross`. The comparison prints a t-statistic of the average trade, because a few dozen trades in one regime cannot show an edge, and on 90 days none of the five strategies is more than 1.5 standard errors from zero. Widening the pullback from 0.5 % / 1 % to 5 % brought more signals, not more trades (five places) and no better result.
- **Which threshold the owner meant by "1 % to 5 %" is not certain.** The only setting at exactly 1 % was `MAX_TOTAL_PLANNED_OPEN_RISK_PCT`, which was changed (see below). The strict original's pullback threshold is also 1 % and the stable one's is 0.5 %; if those were meant, they are the `_5pct` strategies, and the comparison above is the answer to what that does.

- **The database is archived outside Docker, automatically (owner's order).** With the data in a Docker volume, a reset of Docker Desktop or one wrong `down -v` would lose everything, and nothing had a copy. The `backup` container writes a checked, compressed snapshot (SQLite backup API, not a file copy) to `./var/backups` on the PC every 6 hours and keeps a week of them. The archive folder is a bind mount, which is safe here because it holds finished single files, not a live database. A snapshot is verified before it is kept, written under a temporary name, and old ones are pruned only after a new one exists. Restoring was tried on a scratch volume. What it does not protect against: the PC's disk itself (copy `var/backups` elsewhere if that matters) and a database that was already wrong when it was archived.

- **The backtest shows the strategy the live loop's window and asks only about symbols that could signal (Phase 3.3).** Showing the whole file (with the future in it, and years of warm-up before the first bar) was not what the live loop sees; the window is `LOOKBACK_DAYS` of 15-minute and `HTF_LOOKBACK_DAYS` of 1-hour bars that started before now. The prefilter is exact, not an approximation: it only skips symbols whose last closed bar cannot be a cross-up with the RSI in its band, and it keeps a margin so that a borderline bar is still passed to the strategy, which decides. It is switched off with `prefilter=False`, and a test compares both ways trade by trade. 131 s became 3.6 s, so a walk-forward over many windows (3.4) and a comparison of strategies (3.3a) are practical. Slippage is reported as a breakdown of what is already in the prices.

- **The data lives in Docker, in one place (owner's order).** The whole database (`trading.db`) and the log are in the named volume `alpaca_trader_var`; the trading loop (`alpaca-trader`, dry-run) and the hourly candle update (`alpaca-trader-data`) run as containers on it. Moved, not copied: after a verified snapshot was loaded into the volume and the state checked there, the host's `var/trading.db` was deleted, so the system has no second, diverging copy. Why a volume and not a folder on the host: SQLite in WAL mode does not work reliably over a Windows bind mount, and a Linux volume does. Why two containers: the loop and the candle download restart independently. The cost: commands are run with `docker compose exec`, a code change needs a rebuild, and the loop only runs while Docker Desktop does. Two processes write to one SQLite file, so connections wait up to 30 s for the lock.

- **The backtest uses the real `RiskEngine` and the live entry plan (Phase 3.1).** No second copy of the sizing and the limits: a copy had already drifted (it knew nothing of the five-position limit, the gross cap, the total risk or the daily loss guard). `RiskEngine` takes a `clock`, so the same code judges a signal from last month; the live system keeps the real time. The entry is modelled the way the live loop does it: decision 30 s after the bar closes, the first print of the next bar as the price (it has to pass the live price check), a marketable limit that fills at once at price plus slippage and never above the limit, stop and target where the plan puts them. The earlier model (limit at the signal bar's close, filled from the bar after next) is gone: the live system never waits for a dip. The effect on the 90-day replay is large (-1.56 % to -0.01 %) with the strategy unchanged, which is the reason to model fills carefully before reading anything into a backtest result.

- **`MAX_TOTAL_PLANNED_OPEN_RISK_PCT` goes from 1 % to 5 %** (owner's order; it was the only threshold set to exactly 1 %). Default in `config.py` and `.env.example`. Paper only. With the other limits unchanged this does not change what the risk engine approves: one position risks at most 0.2 % of equity (`MAX_PLANNED_RISK_PER_TRADE_PCT`), a 4 % position with a 4 % stop risks about 0.16 %, and the 20 % gross exposure cap allows five of them, so open risk tops out near 0.8 % and never reached the old 1 % either. The limit only starts to matter if the position size, the per-trade risk or the gross exposure cap are raised too.

## Decisions of 2026-11-05

- **Strategy research: first pass, nothing passes; the daily signals are parked (owner).** 14 variants of two signals (12-1 month momentum, one-week reversal) on 144 large stocks and SPY, 2016 to 2026-05-04, against criteria fixed before any result: none reaches net t >= 3. Momentum has a weak same-direction sign (about +0.5 % over 20 days, t about 2 before costs, 1.6 after); reversal has nothing after the 0.10 % cost. The hold-out (from 2026-05-05) is untouched and cannot be loaded by the measurement. See `strategy-research-plan.md`, section 9.
- **Daily bars are always from SIP (full market), in `var/research.db`.** The free IEX feed starts in 2020 and carries 2 to 3 % of the real volume. The file is a cache of its own, outside `trading.db`.
- **News: Alpaca's news API into a cache of its own, `var/news.db`; no chunking, no embeddings.** Two tables, `news_articles` and `news_symbols`; the question the Oracle asks is "what was said about this symbol in the last day", a lookup by symbol and time. Alpaca keeps its news from 2015, so the file is a cache; what it holds that Alpaca cannot give back is when we first saw an article. The container `alpaca-trader-news` refreshes it every 5 minutes.
- **News to the Oracle: chosen, cleaned and bounded (`oracle/news_input.py`).** Up to 5 articles that the cache had stored by then: 3 from the last 24 hours and 2 from the rest of the last week (the owner's change the same night: a quiet day still shows the earnings of three days ago), each with its age in hours so that a week-old article cannot pass for today's; round-ups of more than 3 symbols left out (measured the same night on a week of the real cache: 5 let through the 4- and 5-name round-ups and other companies' stories tagged to the stock, 3 removes them with almost nothing real lost, 2 starts to lose real two- and three-company stories; preferring a headline that names the company or ticker was tried and rejected, because it favours round-ups that list every name and misses short names such as 3M), one story once whichever source or day, each as a one-line headline (160 characters) and summary (300) without addresses, markup, template tokens or invisible characters; the ids shown are journalled. Cleaning cannot recognise an instruction in plain words; what limits the harm is that the Oracle only answers a signal that exists and the risk engine decides the order. Putting the text in the prompt as quoted data is the provider's part (2.2).
- **Chroma and the RSS pipeline are removed** (code, settings `RSS_*`, `CHROMA_*`, `CHUNK_*`, `EMBEDDING_PROVIDER`, `RETRIEVAL_TOP_K`, and the dependencies `chromadb`, `feedparser`, `beautifulsoup4`, `httpx`, `tenacity`, `respx`). The lock file went from 128 to 74 packages, the five Chroma security ignores are dropped with it, and PyYAML became an explicit dev dependency (the safety-policy test had it only through Chroma). Should RSS come back as a second news source, it goes into the same news cache with a `source` of its own.
- **Oracle and risk order (owner's proposal, for 2.2):** risk as a cheap pre-check, then the Oracle, then risk again with a fresh account snapshot; see `action-plan.md`, section 0.4, item 17.

## Decisions of 2026-11-06

Task 2.2, the Oracle provider (the owner's brief of 2026-11-05 evening, in full in `oracle-provider-task.md`):

- **The model is called only through the Go backend** (`POST /oracle/evaluate`, bearer token = the backend's `ORACLE_TOKEN`). The bot never calls Lemonade directly (that would bypass the backend's slot limiter and could clog the chat), never uses the backend's database or library, and never sends it Alpaca keys. The Flet app only watches, through the backend. The backend's repository is not touched from here.
- **Shadow mode first** (`ORACLE_MODE=shadow`, the default). The loop gets `APPROVE` whatever the model said; the model's real answer is stored in `oracle_decisions` with the mode. `active` is a later switch, and an "owner confirms" mode is a later, separate decision.
- **Risk keeps the last word; nothing unclear is a yes.** A timeout, a refused call, a reply that is not JSON, an unknown verdict or a missing field is a `HOLD` marked `failed`. The model never chooses a symbol, a size or a price.
- **The network works, and item 14 of the action plan was wrong.** The backend listens only on `127.0.0.1:8080` and the container still reaches it as `http://host.docker.internal:8080` (Docker Desktop forwards to the PC's loopback). No second port is needed. Side effect: every container on this PC can reach the whole backend, and only the two Oracle routes need a token there.
- **Timeout 10 s** (`ORACLE_TIMEOUT_SECONDS`). The backend answers in 1.4 to 2.5 s; if the bot stops waiting, the backend finishes the call and the next question about the same signal finds the answer in its cache (a `HOLD` for 3 minutes, `APPROVE` or `VETO` for 30).
- **The Oracle is switched on in shadow mode (2026-11-06, 16:00 UTC).** `ORACLE_ENABLED=true` and `ORACLE_PROVIDER=backend` in the bot's `.env`; the token already there under the backend's name (`ORACLE_TOKEN`) reaches the container through `compose.yaml`. `oracle-probe` showed the road works (token accepted, `Gemma-4-12B-it-GGUF` answered in 1.1 s, the row is in `oracle_decisions`). The loop's orders do not change. Two fixes came with it: the shadow export no longer plays an outage or a HOLD as a veto, and a backtest consults the Oracle only when it is given a replay file (with `ORACLE_ENABLED=true` and no file it used to refuse every signal).
- **The weekly-signal experiment runs forward in time first, with no orders (owner, 2026-11-06: "do the experiment, even several if needed").** A momentum paper account needs a daily schedule, a time-based exit and a wide protective stop, none of which the order engine has, and the first paper order of a new strategy needs the owner's explicit yes (research plan, question 6); so stage 1 records each evening what `momentum_12_1` would pick, before the prices exist, and judges it later with the same measurement as the development part (`research/forward.py`, container `alpaca-trader-forward`). More past history was rejected for now: the list is today's large companies, and the longer the history the more it flatters buying past winners. Rules and criteria are in `strategy-research-plan.md`, section 10, written before the first record. Stage 2 (real paper orders) is not built.
- **The repository is to be made private (owner, 2026-11-06).** Consequence: the unauthenticated GitHub API no longer answers, so CI can only be checked from the Actions page, or with the `gh` CLI once the owner has logged in to it.
- **The Oracle observer (owner, 2026-11-06: "do it").** The live strategy runs over the research universe less the watchlist (about 133 symbols) in a container of its own, `alpaca-trader-observe`, and each signal is put to the Oracle as the live loop does it; no order is placed (the cycle has no risk or execution engine). Bars come from a store of their own, `var/observe.db`, not from a download per cycle (155 symbols would take minutes). The criteria for judging the model are unchanged except that these signals join the sample; the change is written in oracle-provider-task.md, section 5. The signal-level judge for them is not built yet.
- **Hours: the opening-range breakout is measured as a signal, not run in the backtest (owner: "do it").** The backtest holds positions with a 4 % stop and a 5 % target and has no end-of-day exit, so it cannot test an intraday strategy; `measure-intraday` takes the signal's own window (next bar open to session close). One variant, `orb_30m_long`, defined in strategy-research-plan.md, section 11, before any result; it is variant 15.
- **Bars are downloaded 25 symbols a request and written as they arrive** (`data/history.py`). One request for ~150 symbols of 15-minute bars paged for a quarter of an hour and everything was lost if it failed late.
